# GitHub Pages and Firebase Deployment Guide

This guide records the complete setup used to host Finance at:

`https://shubham-code-lab.github.io/Finance/`

It is also a reusable checklist for deploying another Vite, React, and Firebase application.

## 1. How the deployment works

There are three separate systems involved:

1. **Vite** compiles the React and TypeScript source into static HTML and JavaScript.
2. **GitHub Actions** builds the application and commits the compiled files to `main`.
3. **GitHub Pages** serves those compiled files from the repository root.

Firebase is not hosting the frontend. It provides Authentication and Firestore to the frontend hosted by GitHub Pages.

The important repository paths are:

```text
Finance/
|-- finance-code/              # React/Vite source code
|   |-- src/
|   |-- index.html             # Vite source template
|   |-- package.json
|   `-- vite.config.ts
|-- assets/                    # Compiled production files generated by Actions
|-- index.html                 # Compiled production entry generated by Actions
|-- 404.html                   # SPA fallback generated by Actions
|-- .nojekyll                  # Prevents Jekyll processing
|-- release.json               # Release number and publish switch
|-- firestore.rules
|-- firestore.indexes.json
|-- firebase.json
`-- .github/workflows/
    |-- ci.yml
    `-- publish.yml
```

Do not manually edit the root `index.html`, `404.html`, or `assets/`. They are build output and are replaced by the publish workflow.

## 2. Why source code is in `finance-code/`

GitHub Pages serves static files. It cannot compile TypeScript or understand this Vite source reference:

```html
<script type="module" src="/src/main.tsx"></script>
```

When the source `index.html` was served directly from the repository root, the browser requested `/src/main.tsx` and received HTTP 404.

The solution was to keep source code in `finance-code/` and reserve the repository root for Vite's compiled output. After a production build, the root HTML refers to a generated file such as:

```html
<script type="module" src="/Finance/assets/index-b0r7pjOW.js"></script>
```

That JavaScript file exists in the root `assets/` directory and can be served by GitHub Pages.

## 3. Create and configure Firebase

### Create the project and web app

1. Open the [Firebase Console](https://console.firebase.google.com/).
2. Create or select a Firebase project.
3. Open **Project settings > General**.
4. Under **Your apps**, create a Web app using the `</>` button.
5. Firebase displays a configuration object containing:
   - `apiKey`
   - `authDomain`
   - `projectId`
   - `storageBucket`
   - `messagingSenderId`
   - `appId`

The Firebase Web API key identifies the Firebase project. It is included in the browser bundle by design; it is not a server or service-account private key. Data protection must come from Firebase Authentication, restrictive Firestore rules, API-key restrictions where applicable, and never exposing a service-account private key.

### Enable Google authentication

1. Open **Firebase Console > Authentication > Sign-in method**.
2. Enable **Google**.
3. Select the support email and save.
4. Open **Authentication > Settings > Authorized domains**.
5. Add the GitHub Pages hostname:

```text
shubham-code-lab.github.io
```

Use only the hostname. Do not add `https://`, `/Finance/`, or a trailing slash.

Keep `localhost` authorized for local development.

### Create and secure Firestore

1. Open **Firestore Database** in Firebase Console.
2. Create the default database in Production mode.
3. Choose the intended region; this project prefers `asia-south1` when available.
4. Publish the rules from `firestore.rules`.
5. Deploy or create the indexes described by `firestore.indexes.json` when required.

The current rules allow an authenticated user to access only documents under that user's path:

```text
/users/{uid}/...
```

Everything else is denied. GitHub Pages is public, so Firestore rules—not the website URL—are the security boundary for finance records.

Never place a Firebase Admin SDK or service-account JSON key in a Vite application, GitHub Pages bundle, `.env`, or `VITE_` variable. Any `VITE_` value is compiled into browser-readable JavaScript.

## 4. Configure Firebase locally

Copy `finance-code/.env.example` to `finance-code/.env` and replace the placeholder with the values from the Firebase web-app configuration:

```dotenv
VITE_FIREBASE_API_KEY=your_real_web_api_key
VITE_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=your-project
VITE_FIREBASE_STORAGE_BUCKET=your-project.firebasestorage.app
VITE_FIREBASE_MESSAGING_SENDER_ID=your_sender_id
VITE_FIREBASE_APP_ID=your_web_app_id
VITE_QUOTE_PROXY=
VITE_NSE_PROXY=
```

The local `.env` file is ignored by Git and must not be committed.

`VITE_NSE_PROXY` is optional. When empty, Finance requests the Nifty 500 CSV directly from NSE. Configure it only if a deployed browser request is blocked and a trusted proxy has been created.

`VITE_QUOTE_PROXY` is the base URL of the production Yahoo Finance proxy. It can remain empty locally because the Vite development server proxies `/market/yahoo`. The GitHub Pages build sets it to the deployed Cloudflare Worker URL.

### Yahoo Finance production proxy

Yahoo Finance does not include an `Access-Control-Allow-Origin` response header for the search, chart, or fundamentals endpoints used by Finance. A browser therefore blocks direct requests from GitHub Pages even when Yahoo returns HTTP 200. Command-line tools such as `curl` are not subject to browser CORS enforcement.

GitHub Pages cannot run a server-side proxy. Finance uses a Cloudflare Worker whose source is stored in `cloudflare-worker/yahoo-proxy.js`. The Worker:

- accepts the GitHub Pages origin;
- permits only `GET` and CORS preflight requests;
- allowlists the three Yahoo endpoint families used by the application;
- forwards no Firebase credentials or user finance data;
- retries `query2.finance.yahoo.com` when `query1` returns HTTP 429;
- caches successful Yahoo responses for five minutes;
- adds the required CORS response headers.

Opening the Worker's root URL returns `Yahoo endpoint not allowed` by design. Test an allowlisted route such as:

```text
WORKER_URL/v1/finance/search?q=Mahindra&quotesCount=12&newsCount=0
```

The production Worker URL is public configuration, not a secret. It is assigned to `VITE_QUOTE_PROXY` in `.github/workflows/publish.yml`. If the Worker URL changes, update that workflow and publish a new release.

Run the application locally:

```bash
cd finance-code
npm install
npm run dev
```

Before publishing, run:

```bash
npm run check
```

This runs linting, formatting validation, tests, and a production build.

## 5. Add GitHub Actions repository secrets

Open the GitHub repository and go to:

**Settings > Secrets and variables > Actions > Secrets > Repository secrets**

Create these six separate secrets. Their names must match exactly:

```text
VITE_FIREBASE_API_KEY
VITE_FIREBASE_AUTH_DOMAIN
VITE_FIREBASE_PROJECT_ID
VITE_FIREBASE_STORAGE_BUCKET
VITE_FIREBASE_MESSAGING_SENDER_ID
VITE_FIREBASE_APP_ID
```

For each secret, copy only the value. Do not copy the variable name or `=` sign.

Correct:

```text
AIza...actual-key...
```

Incorrect:

```text
VITE_FIREBASE_API_KEY=AIza...actual-key...
```

Do not create one secret named `FIREBASE_SECRET`; the workflow reads the six exact names above. Do not put them under Actions Variables, Codespaces secrets, or Environment secrets unless the workflow is changed to use those locations.

The API-key secret must contain the real Firebase web API key, not the example placeholder `YOUR_MANUALLY_RETRIEVED_WEB_API_KEY`.

## 6. Configure the Vite base path

A GitHub project site is hosted below the repository name, not at the hostname root. For this repository the path is `/Finance/`.

`finance-code/vite.config.ts` reads the base path from the build environment:

```ts
export default defineConfig({
  base: process.env.BASE_PATH ?? '/',
})
```

The publishing workflow sets:

```yaml
env:
  BASE_PATH: /Finance/
```

For another repository, replace `Finance` with the exact repository name, including capitalization. A wrong base path normally causes the HTML to load while JavaScript and other assets return 404.

## 7. Configure GitHub Pages

Open:

**GitHub repository > Settings > Pages**

Choose:

- Source: **Deploy from a branch**
- Branch: **main**
- Folder: **/(root)**

This project does not use `docs/` for deployment. GitHub Pages can publish either `/(root)` or `/docs`, but the repository and workflow must use the same choice. Finance deliberately uses the root to match the Portfolio repository structure.

The `.nojekyll` file prevents GitHub's Jekyll processing from changing or ignoring generated frontend assets.

## 8. CI workflow

`.github/workflows/ci.yml` runs on pushes and pull requests targeting `main`. It:

1. Checks out the repository.
2. Installs Node.js 22.
3. Caches packages using `finance-code/package-lock.json`.
4. Runs `npm ci` inside `finance-code/`.
5. Runs `npm run check`.

This catches lint, formatting, test, TypeScript, and build failures before merge.

## 9. Publishing workflow

`.github/workflows/publish.yml` runs on pushes to `main` and can also be started manually with **Actions > Publish site > Run workflow**.

On a normal push, it publishes only when `release.json` contains:

```json
{
  "version": "1.0.5",
  "publish": true
}
```

The workflow then:

1. Checks out `main`.
2. Reads the `publish` switch.
3. Installs dependencies in `finance-code/`.
4. Makes the Yahoo proxy URL and six GitHub secrets available to Vite.
5. Verifies none of the Firebase values is empty.
6. Builds with `BASE_PATH=/Finance/`.
7. Removes the previous compiled root `assets/`, `index.html`, and `404.html`.
8. Copies `finance-code/dist/` to the repository root.
9. Copies `index.html` to `404.html` for SPA route fallback.
10. Creates `.nojekyll`.
11. Changes `release.json` back to `"publish": false`.
12. Commits the generated files to `main` as `github-actions[bot]`.

The generated commit includes `[skip publish]` in its message. The workflow checks for that marker so the bot's commit does not start an infinite publish loop.

The workflow requires:

```yaml
permissions:
  contents: write
```

If branch protection blocks the generated commit, permit GitHub Actions to bypass only the necessary rule, or replace this design with GitHub's artifact-based Pages deployment. Keep force pushes and branch deletion blocked.

## 10. Publish a new version

For an ordinary release:

1. Finish and validate the source changes in `finance-code/`.
2. Increase the version in `release.json`.
3. Change `publish` to `true`.
4. Commit and push or merge the change into `main`.
5. Open **GitHub > Actions** and confirm both **CI** and **Publish site** pass.
6. Wait for **pages build and deployment** to pass for the generated bot commit.
7. Open the live site and hard-refresh if necessary.

Example:

```json
{
  "version": "1.0.5",
  "publish": true,
  "feature": [],
  "bugfix": [],
  "refactor": [],
  "other": []
}
```

Adding or changing a GitHub secret does not automatically rerun an already failed workflow. After fixing a secret, use **Run workflow** or push a new release commit.

## 11. Verification checklist

After deployment, verify:

- `https://USERNAME.github.io/REPOSITORY/` returns HTTP 200.
- Page source loads `/REPOSITORY/assets/index-....js`, not `/src/main.tsx`.
- The JavaScript asset returns HTTP 200.
- **Actions > Publish site** succeeded.
- **Actions > pages build and deployment** succeeded for the generated bot commit.
- Google Sign-In opens without an unauthorized-domain error.
- A signed-in user can read and write only their own Firestore data.
- No statement, spreadsheet, PDF, `.env`, or personal finance export is tracked by Git.

For this project, the expected production script path begins with:

```text
/Finance/assets/
```

## 12. Troubleshooting

### `/src/main.tsx` returns 404

Cause: GitHub Pages is serving Vite's source `index.html` instead of compiled output.

Fix: build the application, publish `dist/` to the configured Pages folder, and ensure Pages points to `main` and `/(root)` for this repository.

### Firebase configuration is missing

Cause: one or more `VITE_FIREBASE_*` values were absent when GitHub Actions ran `npm run build`.

Fix: add all six exact Repository secret names, then start a new workflow run. Secrets are injected during compilation; changing a secret does not modify an already-built JavaScript file.

### Workflow says a Firebase secret is not configured

Check that the secret:

- is in the correct GitHub repository;
- is under **Actions > Repository secrets**;
- uses the exact uppercase name;
- is not stored only as a variable, Codespaces secret, or unrelated environment secret.

### Firebase API key is invalid

Check that `VITE_FIREBASE_API_KEY` contains the `apiKey` value from the Firebase web-app configuration. Do not use the placeholder from `.env.example`, a service-account key, or the whole `VITE_FIREBASE_API_KEY=...` line.

### Google Sign-In reports an unauthorized domain

Add `USERNAME.github.io` under **Firebase Authentication > Settings > Authorized domains**. Do not enter the protocol or repository path.

### Site still shows the previous version

1. Confirm Pages completed for the latest generated bot commit.
2. Open the site in a private window or press `Ctrl+Shift+R`.
3. Inspect page source and compare the generated asset filename with the root `index.html` on `main`.

### Assets return 404

Check that `BASE_PATH` exactly matches `/<repository-name>/` and includes both slashes.

### Yahoo requests fail with a browser CORS error

Do not call Yahoo directly from GitHub Pages and do not use `mode: "no-cors"`; an opaque response cannot be read as JSON. Confirm `VITE_QUOTE_PROXY` was present during the production build, then test the Worker's full `/v1/finance/search`, `/v8/finance/chart/...`, or fundamentals route. The Worker root is intentionally not a valid Yahoo endpoint.

### Yahoo proxy returns HTTP 429

Confirm the deployed Worker matches `cloudflare-worker/yahoo-proxy.js`. It sends browser-compatible headers and retries Yahoo's `query2` host when `query1` is rate-limited. Yahoo Finance is an unofficial dependency and may still impose rate limits or change behavior.

### Publish workflow cannot push to `main`

Check workflow `contents: write` permission, repository Actions permissions, and branch rules. If `main` requires pull requests, configure a narrowly scoped GitHub Actions bypass for the generated site commit.

## 13. Security and privacy rules

- Never commit `.env`.
- Never commit bank statements, personal PDFs, Excel exports, or data backups.
- Never put service-account credentials in frontend code or GitHub Pages.
- Treat the compiled site as public; anyone can download its JavaScript.
- Protect personal records with Authentication and Firestore security rules.
- Keep each user's records under `/users/{uid}`.
- Review Firestore rules before changing collection paths.
- Restrict the Firebase Web API key to the APIs and browser referrers needed by the application when appropriate.
- Keep `main` protected, require CI, and block force pushes and deletion.

## 14. Reusing this setup for another project

When copying this setup, change all project-specific values:

1. GitHub repository name and Pages URL.
2. `BASE_PATH` in the publish workflow.
3. Firebase project and Web app.
4. The six GitHub repository secrets.
5. Firebase authorized GitHub Pages hostname.
6. Firestore rules, indexes, and collection paths.
7. The allowed GitHub Pages origin and deployed URL in the Yahoo proxy.
8. The live-site link in the README.

Keep source and generated output separate, and verify the generated HTML before considering the deployment complete.
